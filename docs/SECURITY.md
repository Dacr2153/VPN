# VPNForge Security

## Threat Model

VPNForge is designed to protect against the following threat classes:

| Threat | Description | Mitigation |
|--------|-------------|-----------|
| Traffic interception | ISP or network MitM reads VPN traffic | Strong AEAD encryption (ChaCha20-Poly1305 / AES-256-GCM) |
| DNS leaks | DNS queries bypass VPN tunnel | DnsGuard overwrites /etc/resolv.conf + kill switch |
| VPN dropout leaks | VPN drops → traffic flows unencrypted | Kill switch (nftables/iptables firewall rules) |
| Key extraction via coredump | Process crash leaks key material | `prctl(PR_SET_DUMPABLE, 0)` |
| Key extraction via swap | Keys written to disk | `mlockall(MCL_CURRENT|MCL_FUTURE)` |
| Privilege escalation | setuid abuse | `prctl(PR_SET_NO_NEW_PRIVS, 1)` |
| Replay attacks | Attacker replays captured packets | WireGuard replay window (anti-replay counter) |
| Handshake downgrade | Force weak cipher | Noise_IKpsk2: no cipher negotiation |
| Key reuse | Long-lived session keys | WireGuard key rotation (every 3 min / 1 GiB) |
| Memory side-channels | Keys readable in memory after use | `Zeroizing<[u8;32]>` — zeroize on drop |

## Cryptographic Design

### Key Storage

All private key material is held in `Zeroizing<[u8; 32]>`:

```rust
// Zeroize on drop — zeroes the backing memory when the struct is dropped
use zeroize::Zeroizing;

pub struct WgPrivateKey {
    inner: Zeroizing<[u8; 32]>,
}
```

This ensures that when the struct goes out of scope, the raw bytes are overwritten before the allocator reclaims them.

### WireGuard Crypto

WireGuard uses the **Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s** handshake pattern:

- **X25519**: Elliptic-curve Diffie-Hellman for session key establishment
- **ChaCha20-Poly1305**: Authenticated encryption for all packets
- **BLAKE2s**: Handshake hash/MAC (keyed)
- **PSK**: Optional pre-shared key for post-quantum resistance (second layer)

Transport keys are rotated every **3 minutes** or **1 GiB** of data, whichever comes first. This limits the blast radius of any single session key compromise.

### AES-256-GCM (OpenVPN data channel)

Implemented via the `ring` crate:

```
Key length:   256 bits (32 bytes)
Nonce:        96-bit random (12 bytes) from ring::rand::SecureRandom
Tag:          128 bits (16 bytes)
AAD:          Session ID + sequence number (replay prevention)
```

### ChaCha20-Poly1305 (alternative cipher)

```
Key length:   256 bits (32 bytes)
Nonce:        96-bit (12 bytes) — counter-based, monotonically increasing
Tag:          128 bits (16 bytes)
```

Both ciphers are **authenticated encryption** — any tampering of ciphertext, nonce, or AAD will cause decryption to fail with an explicit error.

## Process Hardening

The daemon applies these hardening measures at startup (`harden_process()`):

```rust
// 1. Disable core dumps — prevents key extraction from crash files
prctl::set_dumpable(false).ok();

// 2. No new privileges — even via setuid binaries
prctl::set_no_new_privs().ok();

// 3. Lock all memory pages — prevent key material from being swapped to disk
//    MCL_CURRENT (1) = lock current pages
//    MCL_FUTURE  (2) = lock future mmap'd pages
libc::mlockall(3);
```

**Capabilities model:**

The daemon requires only `CAP_NET_ADMIN` (for TUN/routing) and should be run without `CAP_SYS_ADMIN`. After initialization, unused capabilities should be dropped (future: `capset()` to drop all except `CAP_NET_ADMIN`).

## Kill Switch

The kill switch uses a default-deny firewall policy when activated:

### nftables ruleset (preferred)

```nft
table inet vpnforge_ks {
  chain output {
    type filter hook output priority 0; policy drop;
    oif lo accept
    ip daddr <server_ip> tcp dport <port> accept   # VPN tunnel traffic
    ip daddr <server_ip> udp dport <port> accept
  }
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ip saddr <server_ip> accept
  }
}
```

### iptables fallback

```bash
iptables -P OUTPUT DROP
iptables -A OUTPUT -o lo -j ACCEPT
iptables -A OUTPUT -d <server_ip> -p tcp/udp --dport <port> -j ACCEPT
```

The rules **persist even if the VPN connection drops**, ensuring no traffic leaks while the kill switch is active.

## DNS Leak Prevention

When connected, `DnsGuard` writes `/etc/resolv.conf` to use only the VPN-provided DNS server:

```
# Generated by VPNForge — do not edit
nameserver 10.0.0.1
options ndots:0 timeout:2 attempts:2
```

On disconnect, the original `/etc/resolv.conf` is restored from a backup stored at `/run/vpnd/resolv.conf.bak`.

**Known limitation**: On systems using `systemd-resolved`, the symlink `/etc/resolv.conf → /run/systemd/resolve/stub-resolv.conf` must be handled via `resolvectl` instead of direct file write. This is tracked as a future improvement.

## gRPC API Security

The control socket (`/run/vpnd/control.sock`) is:
- Owned by `root:root` or `root:vpnd`
- Mode `0600` or `0660`
- Unix domain socket (not network-accessible)

There is **no authentication** on the gRPC API — access is controlled entirely by file system permissions. This means:
- Only root or members of the `vpnd` group can send commands
- No risk of remote exploitation of the control API

## Known Limitations / Future Work

| Issue | Severity | Plan |
|-------|----------|------|
| No seccomp filter | Medium | Add `libseccomp` or `seccomp` crate to whitelist required syscalls |
| DNS /etc/resolv.conf not using O_NOFOLLOW | Low | Fix symlink race condition |
| No systemd-resolved integration | Low | Use `resolvectl` API when detected |
| No user namespace isolation | Medium | Consider `unshare(CLONE_NEWUSER)` for extra isolation |
| No AppArmor/SELinux profile | Medium | Provide policy files for major distributions |
| `import_profile` RPC unimplemented | Low | Parse .ovpn format and store profile |
